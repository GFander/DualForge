## 二、贯穿项目的审查方法论

### 2.1 事实标签体系（核心纪律）

```
[F]    Source Fact        —— 本项目字节码直接证明
[F-j]  JDK Spec Fact       —— 由 JDK 规范保证，非本项目字节码
[E]    Experimental Fact   —— 本次实验中实际观察到的
[H]    Hypothesis          —— 合理但未被证明
[D]    Design Decision     —— 架构决策
```

判据：任何无法由日志、源码或调用链证明的结论，必须归入 [H] 或 UNKNOWN。

### 2.2 五条核心纪律

| 纪律 | 应用场景 |
|---|---|
| 从正例不反推必要条件 | 一个成功案例不构成必要条件；必要条件必须由负对照实验确认 |
| 单路径结论限定单路径 | 一个已验证路径上的结论，不得外推为系统级事实 |
| Java ModuleLayer ≠ ModLauncher Layer | 观测 provider Layer 时，必须用 IModuleLayerManager 对象同一性判定（==），不得用 java.lang.ModuleLayer 字符串比较 |
| class loaded ≠ method invoked ≠ stage entered ≠ operation succeeded | 判据必须基于实际调用证据，不得因日志里出现类名就判定阶段进入 |
| CLEAR ≠ 修复成功 | 一个具体类型的缺失被补上，不代表 ABI 断层已解除 |

### 2.3 单因子原则

每次 Spike 只引入一个变量。 若发现需要多变量，拆分为多个子 Spike。

K1 对照（control + treatment）：多一次运行换取"唯一变量"的严格性。即使代价是加一次构建 + 一次运行，也应采用。

### 2.4 边界纪律

· 层 e 进入即 STOP（002-0b Step 2-A）
· 层 e 之后继续观测（002-0c，本次唯一的边界变更）
· 不预设 ⑤ 形态（可能 byte[] / ClassNode / 其它）
· 不预设通道 B 不可注册（即使不在白名单，也须字节码级证据）
· 不拼接孤立证据为连续链（必须同一静态调用路径）

## 四、关键决策记录

### 4.1 早期裁定（架构阶段）

| 决策 | 结果 | 关键理由 |
|---|---|---|
| 单一宿主 | NeoForge 为唯一底层补丁基准 | Forbric 失败证明多宿主共存不可行 |
| SPI 优先 | 通过 IModFileCandidateLocator / IModFileReader / IModLanguageLoader 接入 | 官方预留注入点 |
| 共享优先，隔离可选 | 默认共享 Game Layer | 隔离会破坏 instanceof / ServiceLoader |

### 4.2 核心裁定链（Spike 阶段）

**Spike-000 裁定**：FAIL 于 Discovery 阶段的 MINECRAFT_FORGE——发现位置比预期更早（预期 Metadata）。这修正了 v1.1 §14.2 的预判。

**Spike-001a 裁定**：IModFileReader / IModFileCandidateLocator 通过 ModDirTransformerDiscoverer 进入 SERVICE Layer（不是手册预期的 Plugin Layer）。这修正了 v1.1 §3.1。

**Spike-001b-3 裁定**：内置 javafml = BOOT 层；兼容层 = SERVICE 层；同名覆盖 = 情况 A（兼容层胜出）。

**Spike-001b-5/6 裁定**：IModFileInfo / IModInfo 存在三层类型契约（ModSorter / LoadingModList / ModFileInfo 构造参数）；走真实 ModFileInfo 路径可一次越过两道 cast。

**Spike-001c-2 裁定**：ForgeProbe 实例化在层 c 失败（NoClassDefFoundError: net.minecraftforge.eventbus.api.IEventBus）。这是 ABI 断层的第一次实证。

**Spike-002-0a 裁定**：空壳类型使层 c 通过，暴露层 d——证明"类型存在性"与"类型被接受"是两道独立的门。

**Spike-002-0b Step 1 裁定**：白名单判定 = 精确匹配（Map.get + Set.contains）；正确分支是 A（ASM 描述符重写），B（extends 探针）不适用。

**Spike-002-0b-1b 裁定**：两条候选通道——通道 A（ITransformationService#transformers()）SERVICE 层可达；通道 B（ILaunchPluginService）BOOT 层发现源，对第三方 mods/ JAR 静态不可达。④→⑤→⑥ 在同一静态调用路径上。

**Spike-002-0b Step 2-A v1 裁定**：STOP / 前置配置缺口——v1 §0.3 只含空壳 IEventBus，漏了 observer + service + 真实 ModFileInfo 三项前置。

**Spike-002-0b Step 2-A v1.1 裁定**：PASS——四项前置齐全，层 d 解除 + 层 e 进入。

### 4.3 关键裁定案例（审查方法论）

**案例 1：从正例不反推必要条件**

Spike-001b-5 报告曾写"必须声明 Automatic-Module-Name"，我指出这是从成功案例反推必要条件——改为 [E]（当前实验使用的形态）而非 [F]（必要条件）。

**案例 2：发现执行方漏判**

Spike-002-0b Step 2-A v1 报告 §七 偏差 1 写："第 2 项（真实 ModFileInfo）基线已满足"。我纠正：这是错的。 001b-1 基线的 parser 返回自定义 ForgeModFileInfo，不是 ModFileInfo。Run C 停在语言门早于 LoadingModList，若只恢复 observer，会推进到 LoadingModList 的 CCE，仍不可达层 d。

**案例 3：承认自己的失误**

我在 v1.1 交付时说"上轮输出即冻结正文"——措辞错误，指的是上上轮。Codex 核对时发现 Spike_002-0c.md 不存在并 STOP，判断正确。我采用路径 A：补发完整正文。

**案例 4：前置配置错误 ≠ 探针实现缺陷**

Spike-002-0b Step 2-A v1 STOP 于语言门——这是前置配置错误（observer 缺失），不是探针实现缺陷。Codex 停住的判断正确。修复方式是由决策方给出逐字定义（configOf），而非执行方自写。

## 八、思维模式总结（给下一个智能体）

作为裁判，你的核心动作是：

1. 收到输入（实验报告 / 任务说明书 / 顾问意见）
2. 逐项核对：哪些是 [F]（有字节码证据）？哪些是 [H]（推断）？
3. 识别错误类型：
   · 事实错误（如把 JarContents 当 SecureJar）
   · 推断错误（如从正例反推必要条件）
   · 边界错误（如把静态可达说成运行时发生）
   · 前置错误（如漏列前置配置）
4. 作出裁定：采纳 / 修正 / 拒绝 / 补发
5. 冻结交付：写明不可变更项与边界纪律
6. 处理回写：将结果写入手册

最关键的三条纪律：

1. "一个成功案例不构成必要条件"——正向验证不出必要条件，只有负对照才能
2. "class loaded ≠ stage entered"——不得用日志类名代替调用链证据
3. "边界纪律不能因推进而放松"——层 e 进入即 STOP；方向 2 不预设
